## 검증 방식

- 기존 회원·구독·수집·관리자·상담·탈퇴·분석 검사와 32개 샘플 변조 검사를 유지한다.
- `test_efficiency.py`: 기록 100개 조회의 SQL 수, 다른 회원 작업을 바꾸지 않는 상태 확인, 10,000행씩 만든 실제 테이블의 EXPLAIN (ANALYZE, BUFFERS) 비교.
- 인덱스 비교는 동일 트랜잭션에서 인덱스가 있는 계획과 SAVEPOINT 안에서 해당 인덱스만 제거한 계획을 비교한다. 인덱스 선택·반환 건수 동등성을 검사하고 시간·블록 접근량·추가 인덱스 크기를 기록한다. 전체 데이터·DDL은 마지막에 롤백한다. 운영/공유 DB에서는 실행하지 않는다.
- HTTP 검사는 1,000건/동시 8개와 10,000건/동시 16개를 분리한다. 원본 크롤링 데이터 대신 가상 데이터를 사용하고 실행별 데이터만 삭제한다.
- 임시 기준: 오류 0, 최종 값/행 수 일치, 조회 p95 ≤ 1,000ms, 쓰기 p95 ≤ 1,500ms. 실제 서비스 SLA가 아닌 심각한 퇴행 탐지 기준이다.
- 결과는 Catalog API integration의 `catalog-performance` artifact에 7일 보관한다. `latest.json`, `10000-rows.json`, `query-plans.json`으로 나뉜다.

## 효율성 판단의 한계와 남은 작업

- core는 PostgreSQL·API·마이그레이션·정리 작업만 사용한다. Redis/Celery/AI 의존성은 full 또는 선택 이미지이므로 백엔드 개발에 상시 실행할 필요가 없다.
- API 프로세스 1개당 DB 연결 상한은 catalog 6 + member 4 + support 3 = 13개다. 프로세스/서버 수를 늘리면 함께 증가한다. 이 값은 동시 사용자 수가 아니다.
- 정리는 기본 시간당 항목별 최대 500건이므로 최대 일 12,000건/항목이다. 잠금·참조 관계에 따라 실제 정리량은 적다. 이보다 적재량이 많으면 backlog가 커질 수 있어 batch/주기 측정이 필요하다.
- 상품별 삭제의 잠금/트랜잭션은 최신 재입고를 보존하기 위해 유지했다. 속도만을 위해 무조건 일괄 삭제로 바꾸지 않는다.
- 실제 벡터 모델·차원·데이터가 없어 HNSW 검색 품질, 임베딩 시간/메모리/저장공간은 평가하지 않았다. 현재 exact fallback은 후보가 부족하면 추가 검색 비용이 든다.
- 이미지 파일 I/O, 대규모 탈퇴/기록 삭제, 정리 후 autovacuum, 장시간 CPU/RAM 피크와 수십만~수백만 건은 별도 검증이 필요하다.
- PostgreSQL 계획은 가상 데이터 분포와 캐시에 영향을 받는다. 실행 시간 개선율을 운영 환경의 보장값으로 사용하지 않는다. 실제 OCR·Claude·PG·외부 네트워크·프론트 속도는 포함하지 않는다.
