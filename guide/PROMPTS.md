## 1. 검증 요청 (다른 모델로 교차 검증)

```text
너는 시니어 백엔드 리뷰어다. 저장소 daon217/swproject(꿀픽: 쇼핑 페이지 캡처 → OCR → 상품/식품 추천, 알레르기 경고)에서
브랜치 part/소병선-backend-test 가 origin/maintest 대비 바꾼 내용을 검증해라.

맥락 문서: devlog 브랜치의 README.md, OPEN_ISSUES.md, INDEX.md, journal/*.md, VERIFY.md 를 먼저 읽어라.
운영 전제: 크롤링 데이터는 수집기(최준서 파트, origin/part/최준서-collector)가 주기적으로 DB에 넣는다(실시간 수집 아님).
변경 확인: git diff origin/maintest..part/소병선-backend-test

검증할 것:
1. INDEX.md '해결됨' 항목이 정말 해결됐는지, 새 버그나 회귀를 만들지 않았는지 (코드·SQL·마이그레이션·동시성·트랜잭션·락 순서).
2. 각 로그의 '원인'과 '왜 그렇게 해결했는지'가 코드와 일치하는지. 더 나은 해결책이 있으면 근거와 함께 제시.
3. 예외 처리: 일시 장애/코드 결함/입력 오류가 올바른 HTTP 상태와 retryable 값으로 구분되는지, 비밀값이 응답·로그에 새지 않는지.
4. 보안: 인증 누락, 권한 상승, 레이트 리밋 우회, SSRF(애드픽 URL 변환), SQL 주입.
5. '가정:'/'미확인:'으로 표시된 부분(애드픽 요청 형식 등)의 위험.

출력 형식:
- 첫 줄에 너의 정확한 모델명을 적어라. 결과를 devlog에 남길 때는 journal/YYYY-MM-DD-review-<모델명>.md, 제목 "# [모델명] 검증: ..." 형식.
- 발견마다: 심각도(치명/중요/경미), 파일:줄, 문제, 재현 조건, 수정 제안.
- 추측과 확인한 사실을 구분하고, 확인하지 못한 것은 그렇다고 써라.
- 문제가 없으면 '없음'이라고 쓰고 무엇을 확인했는지 적어라.
코드는 수정하지 마라.
```

## 2. 개발일지 작성 요청 (작업 후 기록)

```text
방금 한 작업을 devlog 브랜치에 개발일지로 남겨라. 이 로그는 나중에 다른 AI 모델이 이어서 작업하거나
검증할 때, 그리고 개발 기록으로 참고하는 용도다.

규칙:
- devlog 브랜치(orphan, 문서 전용)의 LOG_TEMPLATE.md 양식을 따른다.
- 이슈마다: 문제점 / 원인(파일:줄) / 해결 방안(검토한 선택지와 장단점) / 해결(적용 내용·파일·커밋 해시·마이그레이션·환경변수)
  / 왜 그렇게 해결했는지(버린 선택지를 버린 이유, 트레이드오프) / 검증(명령과 통과·실패 수, 검증 못한 것) / 남은 과제.
- 새로 발견한 미해결 문제는 OPEN_ISSUES.md에 추가(번호는 INDEX·OPEN_ISSUES 통틀어 다음 번호). 해결한 문제는 OPEN_ISSUES.md에서 지우고 INDEX.md "해결됨" 표에 추가.
- 미해결 항목에는 운영 전제(수집기 주기 적재 등)에 따른 영향을 적는다.
- 추측과 확인한 사실을 구분한다. 확인 못한 것은 '가정:' 또는 '미확인:'으로 표시한다.
- 비밀번호·API 키·토큰·개인정보는 쓰지 않는다(환경변수 이름만).
- 개발일지 제목은 "# [너의 정확한 모델명] 개발일지 · 날짜 주제"로 시작한다(예: # [Claude Opus 5.5] 개발일지 · 2026-11-25 ...). INDEX.md "작성 AI" 칸에도 같은 이름을 쓴다.
- 개발일지 파일은 journal/YYYY-MM-DD-<주제>-<모델명>.md (예: 2026-11-25-adpick-offer-id-gpt-5.md). 한국어로 쓴다.
- 코드 브랜치에는 로그 파일을 커밋하지 않는다. devlog 브랜치에만 커밋한다.
```

이번 작업: <예: #16 애드픽 API를 offer_id 기반으로 바꾸기>

작업 원칙:

  기존 개발 DB 볼륨은 건드리지 않는다.
- 커밋은 의미 단위로 나누고, 끝나면 '2. 개발일지 작성 요청' 규칙대로 devlog를 갱신.
- push·PR·병합은 내가 승인한 뒤에만.

## 4. 이 로그 체계를 만든 원래 요청 (참고)

> (2026-11-24) 따로 로그 브랜치를 만들어서 다른 AI 모델을 사용할 때, 또는 나중에 개발로그로 참고할 수 있도록 로그를 남기고 싶어.
> 문제점, 원인, 해결 방안, 해결, 왜 그렇게 해결했는지 등 로그를 남길 수 있는 브랜치를 만들어줘.
> 그리고 이 프롬프트 또한 다른 AI에게 간편하게 참고하고 프롬프트로 사용할 수 있게 남겨줘.

> (2026-11-24) 로그 제목은 지금 사용하는 AI 이름으로 해줘.
> (2026-11-24) 개발로그는 사실상 개발일지이고, 아직 미해결된 문제들도 따로 남겨줘. 크롤링 데이터는 서버에 미리 넣어놓을 거야.
> (2026-11-24) 미리 넣는다기보다는 주기적으로 DB에 들어갈 거야. 크롤링하는 부분은 준서 파트에 있고 로직을 다시 한번 살펴봐.
> (2026-11-25) 개발일지 브랜치에 어떻게 점검하고 테스트하고 어떤 걸 사용하여 어떤 방식으로 어떻게 했는지에 대한 것도 그동안 했던 거 포함해서 따로 남겨줘. 다른 AI가 사용할 수 있게 프롬프트도 남겨줘. → METHODS.md, tools/, 이 파일 5~7번

## 5. 전체 점검·테스트 (METHODS.md 방식 그대로)

```text
너는 이 저장소의 점검 담당이다. 저장소 daon217/swproject(꿀픽), 작업 브랜치 part/소병선-backend-test.
devlog 브랜치의 METHODS.md(점검·테스트 방법론)를 먼저 끝까지 읽고 그 순서와 원칙을 그대로 따른다.
같이 읽을 것: README.md, OPEN_ISSUES.md, INDEX.md, VERIFY.md, 최근 journal/*.md 3개.

순서:
1. 최신화: git fetch → origin/maintest에 새 커밋이 있으면 내용을 먼저 검토하고, 조상 관계면
   git merge --ff-only origin/maintest. 앞으로 당길 수 없으면 멈추고 나에게 알려라. (푸시는 내가 허락할 때만)
2. 기존 미해결(OPEN_ISSUES.md) 각 항목이 지금 코드에서도 그대로인지 파일:줄로 재확인.
3. 새 문제 찾기: METHODS.md 3.2 grep으로 지도 만들기 → 3.3 체크리스트 9개 항목(예외 분류, 재시도/영구 정지,
   멱등성·동시성, 도착 순서, 권한, 보안, 팀 파트 사이 계약, 기능 미연결, 운영 전제 대입)을 차례로 적용.
   특히 팀 파트 사이 계약: 앱이 부르는 API 경로 ↔ 백엔드 라우트, enum 값, 알레르기 같은 코드 집합의 철자.
4. 의심되는 것은 짧은 스크립트로 재현해서 확정한다. 재현 못한 것은 '미확인:'.
5. 테스트: VERIFY.md / METHODS.md 4.1 격리 통합 테스트(tools/gen_env.py, tools/run-all.sh), 두 실행 순서,
   그리고 gh pr checks 15 로 CI 확인. 기존 개발 DB 볼륨(kkulpick-db-dev_postgres_data)은 절대 건드리지 마라. 끝나면 down -v.
6. 결과를 devlog에 기록: journal/YYYY-MM-DD-<주제>-<너의 모델명>.md (제목 "# [모델명] 개발일지 · ..."),
   새 문제는 OPEN_ISSUES.md에 다음 번호로, INDEX.md 일지 목록 갱신. 비밀값은 쓰지 마라.

출력(한국어):
- 새로 들어온 커밋 검토 결과
- 새로 찾은 문제: 번호, 심각도(치명/중요/경미/운영), 파일:줄, 재현 방법, 영향(주기 적재 전제), 해결 방안 선택지
- 기존 문제 재확인 표
- 문제없던 것(무엇을 확인했는지)
- 테스트 결과(통과/실패 수, 실행 못한 것)
코드는 내가 고치라고 할 때까지 수정하지 마라.
```

## 6. 문제 하나 고치기 (재현 → 수정 → 테스트 → 기록)

```text
저장소 daon217/swproject, 브랜치 part/소병선-backend-test 에서 devlog OPEN_ISSUES.md 의 #<번호>를 고쳐라.
devlog의 METHODS.md를 먼저 읽고 원칙을 따른다.

1. 원인 확인: 문제를 스크립트나 테스트로 먼저 재현하고, 원인을 파일:줄로 적는다.
2. 해결 선택지 2~3개를 장단점과 함께 비교하고 하나를 고른다. 안전 정보·데이터를 버리는 선택지는 피한다.
   팀 파트 경계(백엔드/추천/워커/수집기/앱)를 넘는 값은 양쪽 철자와 기존 클라이언트 호환을 확인한다.
3. 수정 + 테스트 추가: 단위 테스트, 필요하면 DB 통합 테스트(tests/test_embedding_pipeline.py, services/api/tests/*).
   새 테스트는 수정 전 코드에서 실패해야 한다.
4. 검증: Windows 단위 → 격리 DB 통합(tools/run-all.sh, 두 순서) 전부 통과.
   Windows에서 Python으로 파일을 쓸 때는 newline='' (CRLF로 바뀌지 않게).
5. 커밋: 의미 단위, 메시지에 원인·해결 요약, 끝에 Co-Authored-By 줄. 로컬 apps/mobile 변경 파일은 커밋하지 마라.
   테스트 브랜치 푸시·maintest 반영은 내가 허락할 때만.
6. devlog: journal에 문제/원인/선택지/해결/이유/검증/남은 과제, OPEN_ISSUES.md에서 지우고 INDEX.md '해결됨'에 추가.
```

## 8. 과거 점검·테스트 방법 기록과 게시 후 재검증

```text
저장소 daon217/swproject의 devlog에, 실제 개발 시작(2026-11-04) 이후 GPT가 수행한
점검·테스트 방법을 보완해라. METHODS.md 전체, GPT_METHODS.md, GPT_COVERAGE.md,
PROMPTS.md, LOG_TEMPLATE.md, VERIFY.md, INDEX.md, OPEN_ISSUES.md와 관련 일지/정오표를 읽어라.

이번 요청은 과거 수행 방법의 기록이다. 새로운 전체 서비스 테스트·배포·코드 수정은 별도 요청이 있을 때 한다.
1. GPT 작업의 커밋/PR/당시 실행 보고와 CI job 로그를 대조한다. 다른 AI/팀원 작업을 GPT에 합산하지 않는다.
2. 항목마다 목적, 도구, 환경(OS·런타임·DB·실제/mock), 코드 SHA, 작업 폴더, 사전 설정,
   실제 명령/스크립트, 입력·행동·기대값, 통과/실패/skip 수와 이유, 확인 못한 범위를 기록한다.
3. 확인 가능한 명령은 해당 커밋 파일로 링크한다. 복원한 실행 예시와 실제 수행 이력을 구분한다.
   DB 없는 단위·실제 DB 통합·화면 E2E·부하·모델 품질·문서 검증을 구분하고 서로 다른 실행을 합산하지 않는다.
4. 과거 성공 뒤 드러난 회귀와 다른 AI의 정정도 연결한다. 테스트가 중간에 실패하면 이후 단계는 미실행이다.
5. 기존 journal은 보존하고 새 일지를 작성한다. GPT_METHODS와 색인/대응표를 갱신한다.
   비밀값·개인정보·실제 수집 원문·전체 CI 원문을 복사하지 않는다. 개발 이전 설계/발표자료는 제외한다.
6. 게시 요청이 있으면 devlog 최신 HEAD를 다시 확인하고 동시 변경을 보존하여 반영한다.
7. 게시 후에도 원격 HEAD·본문/blob을 다시 읽는다. 링크·고정 코드 경로/행·명령 출처·숫자/CI 근거를
   다시 대조하고 예상 변경 파일만 바뀌었는지 확인한다. main/maintest의 변경이 있으면 누가 바꿨는지 구분한다.
8. 게시 후 검증 결과는 후속 일지에 검사 대상 커밋·방법·결과·미실시 범위를 적고 색인에 연결한다.
   오류를 찾으면 수정/정정 후 같은 검사를 반복한다. 원격 반영 확인 전 완료로 보고하지 않는다.
```
