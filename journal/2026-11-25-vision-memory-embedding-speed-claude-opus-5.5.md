## #66 Vision 워커 메모리 — 중요(운영 장애)

### 재현 (Docker Desktop, 메모리 7.5GiB)
1. Redis + vision-api + vision-worker(concurrency=1)를 격리 compose로 실행, 합성 상품 페이지 8장(1100×700 ~ 1920×4200, 한글 성분 줄 다수).
2. 분석 4건은 성공(10~22초). **5번째(1280×2600) 한 장에서 워커 메모리 350MiB → 6.7GiB(약 10초) → 커널 OOM으로 SIGKILL.**
3. Celery가 자식 프로세스를 다시 띄우지만 같은 작업이 다시 들어와 또 죽음 — 로그 `WorkerLostError ... signal 9`, 반복 14회 → 21회. 세션은 `processing`으로 남아 상태 API는 300초 동안 결과 없음.

### 원인 좁히기 (각각 새 프로세스, `--memory 7g`)
| 실험 | 결과 |
| --- | --- |
| 글자 영역 찾기(det)만 | 119줄 검출, 0.4초, 최대 **558MiB** — 정상 |
| 인식(rec) 포함, batch=1 | 119줄, 22.7초, 최대 **4.4GiB** |
| rec batch=4 / 16, MKLDNN on | OOM으로 죽음 (MKLDNN은 기본값이 이미 꺼짐 — 원인 아님) |
| 긴 한 줄만 인식(폭 160~1120) | 최대 504~537MiB — 줄 하나는 가벼움 |
| **같은 줄 120번** | 520MiB 고정 — 실행할 때마다 새는 누수 아님 |
| **폭이 모두 다른 120줄** (batch=1) | **7.0GiB까지 증가** |
| 인식 입력 폭을 **하나로 고정**(1920) 후 같은 120줄 | **550MiB 고정**(batch=6이면 790MiB), 속도 동일(약 0.4초/줄) |

**결론:** PaddleOCR 인식 단계는 줄마다 입력 폭(`max_wh_ratio`)을 바꿔서 추론한다. Paddle 추론 엔진은 **새 입력 모양마다 메모리를 잡고 돌려주지 않는다.** 페이지마다 줄 폭이 다르니 분석할수록 메모리가 계단식으로 오른다 — NAS의 "+2.2GiB 후 계속 증가"와 같은 모양. 한 페이지에 줄이 많으면 한 작업만으로 OOM.
부수 원인: `worker_max_tasks_per_child=200`은 작업 수 기준이라 메모리 증가를 막지 못함. 컨테이너 메모리 제한 없음. `task_acks_late=True`라 죽은 작업이 다시 들어와 연쇄 종료.

### 해결 방안
| 방안 | 효과 | 비용 |
| --- | --- | --- |
| **A. 인식 입력 폭 고정**(`TextRecognizer.resize_norm_img`에 고정 비율 전달, 너무 긴 줄은 나눠 인식) | 메모리 고정(측정: 7.0GiB → 0.55GiB) | Vision 코드 몇 줄, 아주 긴 줄 처리 확인 필요 |
| B. Celery `--max-memory-per-child`(예: 1500000 KiB) | 기준 넘으면 작업 후 자식 교체 → 계단식 증가 차단 | 교체 때 모델 다시 로드(수 초) |
| C. 컨테이너 `mem_limit` + 죽은 작업 재전달 막기(`task_reject_on_worker_lost=False` 유지 확인, 재시도 횟수 제한) | NAS 전체 메모리 보호, 연쇄 종료 차단 | 설정 |
| D. PaddleOCR 3.x 업그레이드 | 엔진 쪽 해결 가능성(미확인) | 코드가 2.x API 사용 — 큰 변경 |
권장: **A + B + C** (A가 근본, B·C는 안전망).

## #67 임베딩(벡터화) 느림 — 중요(성능)

### 측정 (격리 DB, 3000건)
| 구간 | 결과 |
| --- | --- |
| DB 쓰기(모델 없이 hash) — 지금 방식(상품마다 커밋) | 5.3~6.2 ms/건, 전체의 95% |
| DB 쓰기 — 배치(32건)마다 커밋 | **2.8 ms/건 (약 2배)** |
| MiniLM 모델(CPU) — 스레드 기본값(=코어 14개) | **34 texts/s** (처음 측정 15~28) |
| 스레드 1 / 2 / **4** / 8 | 79 / 150 / **268** / 285 texts/s |

**원인 1 (가장 큼):** PyTorch가 기본으로 모든 코어를 쓰면서 스레드끼리 경쟁해 오히려 **8배 느려진다.** NAS에서는 Vision(Paddle 스레드)과 CPU를 같이 써서 더 심할 수 있다(미확인: NAS 코어 수).
**원인 2:** `embedding_worker.finish()`가 상품마다 트랜잭션·커밋(+조회 3번, 벡터를 문자열로 변환). 디스크가 느린 NAS에서는 커밋 비용이 더 커진다.
예: 3000건 기준 지금 ≈ 3000/34 + 16초 ≈ **104초**, 개선 후 ≈ 3000/268 + 8초 ≈ **19초**(이 PC 기준).

### 해결 방안
1. `torch.set_num_threads(N)` — 환경변수 `RECO_TORCH_THREADS`(기본 4, 코어 절반 이하)로 `SentenceTransformerEmbedder`에서 설정. 추천 HTTP 서비스(쿼리 임베딩)도 같은 설정.
2. `once()`에서 배치 전체를 한 트랜잭션으로(상품별 실패는 savepoint로 격리 — 지금 `finish`의 중첩 트랜잭션이 이미 savepoint가 됨).
3. (선택) 인코딩 배치 크기 32 → 64~128, lease 조회를 배치 한 번으로.

## 검증 / 미확인
- 모든 수치는 이 PC(14코어, Docker Desktop 7.5GiB)에서 측정. NAS 절대값은 다르지만 원인(모양별 메모리, 스레드 경쟁, 상품별 커밋)은 같다.
- 실제 쇼핑몰 캡처가 아니라 합성 페이지. 줄 수가 많을수록 메모리 증가가 커진다.
- 해결 방안 A의 OCR 정확도 영향(아주 긴 줄이 압축될 때)은 측정하지 않음.
