## 문제점
기존 GPT 일지에는 결과와 일부 명령이 있었지만, 검사 도구·환경·입력/행동/기대값·실패 시 확인 방식이 여러 파일에 분산돼 있었다. 사용자 요청은 최신 방법론 프롬프트를 참고해 그동안 GPT가 실제로 한 방법을 기록하고, 게시 후에도 재검증하는 것이다.

## 원인
결과 요약만으로는 “실제 DB인가”, “mock과 실제 모델을 어디서 나눴는가”, “skip을 어떻게 세었는가”, “다시 실행할 환경은 무엇인가”를 알기 어렵다. 최신 공통 도구는 Claude 작업이므로 과거 GPT 도구로 소급할 수도 없다.

## 해결 (적용 내용)
- [GPT_METHODS.md](../../guide/GPT_METHODS.md)에 도구/역할, 점검 순서, 8개 검사 영역, 실제 명령 발췌, 수행 이력, 놓친 부분과 이어받기 기준을 작성했다.
- PROMPTS 8번에 과거 방법 기록·게시 후 검증용 요청문을 추가했다. 기존 5~7번 및 Claude 도구는 보존했다.
- README·METHODS·INDEX·GPT_COVERAGE에서 새 문서를 연결했다. 기존 일지와 OPEN_ISSUES 판정은 수정하지 않았다.
- GPT 관리자 통합 덮어쓰기의 영향과 후속 Claude 정정을 포함했다. Gemini 귀속이 확인된 코드도 GPT 성과에서 제외했다.
- 2026-11-04 이후 실제 개발만 포함하고 이전 설계/발표자료를 제외했다.

## 왜 그렇게 해결했는지
당시 코드와 실행 환경을 고정해야 다른 AI가 과거 결과와 최신 상태를 혼동하지 않는다. 사용자에게 필요한 것은 테스트 이름 목록만이 아니라 어떤 값과 상태를 보고 통과를 판정했는지다. 새로운 전체 서비스 테스트는 이번 과거 기록 요청과 구분했다.

## 검증
- 최신 PROMPTS 2·5~7, METHODS 전체, README/VERIFY/OPEN_ISSUES/INDEX와 최근 일지·교차 검토 정오표를 읽었다.
- 7개 과거 Actions의 head SHA와 success를 재조회했다. API/성능, 계정 UI, 임베딩 DB, 실제 모델의 4개 job 로그에서 결과를 직접 확인했다.
- 확인 예: 59+32=91 통과와 원본 1 skip; UI 첫 환경 6 통과/1 skip 뒤 별도 pending 1 통과; 임베딩 66+17+62=145 통과·2 skip. 서로 다른 실행을 합산하지 않았다.
- 고정 workflow/스크립트에서 명령, 폴더, 환경변수, 검사 조건을 확인하고 문서 링크·코드 행·마크다운·변경 범위를 검사했다.
- 서비스/DB/브라우저/보안 스캔을 새로 실행하지 않았다. 게시 후 원격 내용과 근거 재대조는 후속 일지로 남긴다.

## 남은 과제 / 주의
- 과거 exact 명령을 확인하지 못한 로컬 보고는 그 한계를 유지한다. 현재 전면 회귀 검사나 실운영 품질 보장으로 쓰지 않는다.
- Actions artifact는 당시 7일 보존 설정이었다. 현재 다운로드 가능 여부와 로그 보존 기간은 별도다.
- 기존 미해결 코드 문제는 OPEN_ISSUES를 따른다. 이 문서 보완으로 이슈를 종료하지 않는다.
