## 시뮬레이션 방법
별도 compose 프로젝트 `kkulpick-sim`(개발 DB와 분리, 끝나고 삭제)에서 실제 배포 순서를 그대로 재현했다.

1. **1단계 (현재 운영 라인 = maintest 코드)**: postgres → migrate → api → embedding-init/worker → recommendation. 임베더는 hash(모델 다운로드 생략).
   - 실제 수집 원본 300건(8개 쇼핑몰, 출처별 crawl run) + 식품 20건 + 가격 변경 2차 수집 100건 적재.
   - 결과: 300건 140~220건/초 적재, v1 벡터 320개, 추천 응답 20~40ms, 6건씩 반환.
2. **2단계 (테스트 브랜치로 업그레이드)**: 같은 DB 볼륨에 새 코드로 `up --build`. 마이그레이션 0010~0012 적용, embedding-init이 v2 계약 등록.
3. **사용자 흐름**: 회원 가입 → page_url 분석 / 식품 분석(땅콩 알레르기) / 캡처 분석(Vision 꺼짐) / 모르는 URL / 12명 동시 분석, 확장 정보 선도착, 관리자 가입→CLI 승인→개요·삭제·목록, 애드픽 미설정, 정리 작업 1회.
4. Vision(PaddleOCR)은 이미지 빌드·모델 다운로드가 커서 **띄우지 않았다** → OCR 경로는 미검증.

## <a id="24"></a>#24 v2 임베딩 전환 직후 추천이 0건 — 미해결 (중요, #12에서 생김)

**문제점** 업그레이드 직후 embedding-worker가 다시 임베딩을 끝낼 때까지 모든 추천(상품·식품)이 **0건**. 실제 모델(MiniLM CPU)과 큰 카탈로그에서는 수 분~수 시간 동안 추천이 비게 된다. hash 320건에서는 워커 시작 후 약 2초 만에 회복.

**원인** #12에서 템플릿을 v2로 바꾸자 추천 서비스가 즉시 v2 계약만 조회하는데, v2 벡터는 백필이 끝나야 생긴다. bootstrap이 v1을 바로 내린다(serving=false).

**해결 방안 (안)**
| 선택지 | 비고 |
| --- | --- |
| A. 블루/그린: v2를 색인하는 동안 조회는 v1 유지, v2 대기 작업이 0이 되면 전환하고 다음 bootstrap에서 v1 정리 | 쿼리 인코더가 같아(템플릿은 문서 쪽만 다름) v1 벡터로 조회 가능. 권장 |
| B. 배포 절차로 해결(전환 전 수동 백필) | 사람 실수에 의존 |
| C. 템플릿 변경 되돌리기(#12 취소) | 브랜드·카테고리 반영 포기 |

## <a id="25"></a>#25 분석 재시도에 대기 시간이 없음 — 미해결

**문제점** Vision이 꺼진 상태에서 캡처 분석이 **2.3초 만에 3회 재시도를 모두 소진**하고 실패. Vision 재시작(배포·OOM)처럼 몇 초짜리 장애에도 그 사이의 분석이 전부 실패한다.

**원인** 백엔드 `/fail`이 retryable이면 즉시 `queued`로 되돌리고, claim이 바로 다시 가져간다. (#05에서 일시 오류를 retryable로 바꾼 뒤 드러남. 이전에는 첫 시도에 바로 실패.)

**해결 방안 (안)** analyses에 `available_at`(다음 시도 가능 시각)을 두고 지수 대기(예: 5초, 20초) 후 claim. 마감(deadline 10분) 안에서만.

## <a id="26"></a>#26 이미지 없는 미매칭 분석이 OCR_FAILED·retryable=true — 미해결

**문제점** 이미지 없이 page_url만 보냈는데 카탈로그에 없으면 `OCR_FAILED`(OCR을 하지 않았는데), 상태 API는 `retryable: true`로 응답. 다시 시도해도 결과가 같다.

**원인** 워커가 제목을 못 얻으면 무조건 `OCR_FAILED`. 상태 API는 `INPUT_INVALID` 외에는 모두 retryable로 표시. 백엔드 Failure.code 목록에 "매칭 없음" 코드가 없음.

**해결 방안 (안)** `CATALOG_NO_MATCH` 코드 추가(이미지 없음 + 매칭 없음), 상태 API에서 OCR_FAILED·CATALOG_NO_MATCH는 retryable=false, 안내 문구 "캡처를 함께 보내 주세요".

## <a id="27"></a>#27 알레르기 사용자의 식품 추천이 항상 0건 — 확인 필요 (데이터)

**문제점** 땅콩 알레르기 사용자의 식품 분석: 완료됐지만 추천 0건 + "페이지 성분을 확인하지 못했습니다" 경고.

**원인** 설계상 성분이 없는 식품은 안전 후보로 보지 않는다. 수집 상품에 성분 데이터(foods.ingredients)가 아직 없다. **버그가 아니라 데이터 부족**.

**해결 방안** 수집기에서 food-evidence 확장(성분·알레르기 표시)을 보내야 한다(#13으로 선도착도 처리됨). 그 전까지는 UI에서 "성분 정보가 있는 상품이 아직 없어요" 같은 안내 필요.

## 기타 관찰
- 배포 중 옛 embedding-worker(1단계 이미지)가 남아 있으면 v1 계약 검증 실패로 재시도 로그만 반복(무해).
- `admin_cli`는 `grant <login_id> --role admin` 형식(위치 인자). `tools/workspace.py admin --login-id`가 이를 감싼다.
- 1단계 적재 중 출처가 다른 관측을 한 crawl run에 섞으면 `RUN_SOURCE_CONFLICT`(설계대로). 수집기는 출처별 run을 써야 한다.
